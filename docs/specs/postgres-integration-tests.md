# مشخصات قابلیت: پوشش integration برای ثبت هم‌زمان مطالعه در PostgreSQL

## شناسهٔ ROADMAP

F-03

## چرا

ثبت مطالعه باید در برابر دو یا چند درخواست هم‌زمان برای یک کاربر و یک روز محلی idempotent بماند. `repositories.readings.mark_read` از `INSERT ... ON CONFLICT DO NOTHING` در PostgreSQL استفاده می‌کند، اما تست DB فعلی اجرای هم‌زمان این قرارداد را بررسی نمی‌کند.

## رفتار از دید کاربر

- رفتار محصول تغییر نمی‌کند.
- اگر چند ثبت هم‌زمان برای همان کاربر و روز برسد، مطالعه فقط یک بار در پایگاه داده ذخیره می‌شود؛ یک فراخوانی موفق گزارش می‌شود و بقیه تکراری‌اند.
- ثبت مطالعه در روزهای متفاوت همچنان مستقل است و در این spec تغییر نمی‌کند.

## اثر روی کل محصول

- مسیرهای کاربر: فقط رفتار موجود `mark_read` در repository پوشش داده می‌شود؛ منو، command، callback، API، پروفایل، خلاصهٔ هفتگی و scheduler تغییری ندارند.
- پنل ادمین: action/KPI/event/filter/report جدیدی لازم نیست؛ این تغییر فقط تست قرارداد پایگاه داده است و رویداد محصولی تازه‌ای تولید نمی‌کند.
- رفتار کاربران موجود: بدون تغییر.
- تعامل با featureهای مرتبط: خواندن از مسیرهای فعلی بات و ثبت در `reading_logs` استفاده می‌کند؛ سرویس‌های freeze و comeback در این تغییر تغییر نمی‌کنند.

## داده و حریم خصوصی

- دادهٔ جدید یا migration لازم نیست.
- تست با شناسهٔ ساختگی و روز ثابت در DB آزمایشی اجرا می‌شود و ردیف‌های خودش را پاک می‌کند.
- هیچ داده‌ای در log یا cache اضافه نمی‌شود.
- تست فقط با `TEST_DATABASE_URL` مخصوص پایگاه دادهٔ disposable اجرا می‌شود؛ استفاده از production ممنوع است.

## حالت‌های خاص

- چند تراکنش مستقل، هم‌زمان یک `(user_id, day)` را ثبت کنند: دقیقاً یک نتیجه `True` و باقی نتایج `False` باشند؛ در DB دقیقاً یک ردیف وجود داشته باشد.
- درخواست‌های متوالی برای همان کلید نیز باید همین قرارداد را حفظ کنند.
- رفتار خطای شبکه، retry بیرونی و تغییر semantics محصول خارج از محدوده است.

## امنیت و مجوز

تست credential یا شناسهٔ کاربر واقعی ندارد. `TEST_DATABASE_URL` باید فقط به PostgreSQL آزمایشی و disposable اشاره کند. هیچ اتصال یا دستور مخربی روی production اجرا نمی‌شود.

## خارج از محدوده

- افزودن یا تغییر منو، handler، API، analytics یا migration.
- بازطراحی تمام پوشش repositoryها یا افزودن زیرساخت جدید CI؛ workflow فعلی PostgreSQL را فراهم می‌کند.
- تست migration از نسخه‌های نصب‌شدهٔ قدیمی؛ CI فعلی migrationها را روی پایگاه دادهٔ تازه اجرا می‌کند.
- تغییر کد `mark_read` مگر اینکه تست مصوب، باگ قابل بازتولیدی را آشکار کند؛ هر اصلاح runtime نیازمند تصمیم جدا و تست regression است.

## تصمیم‌های باز برای مالک

- دامنهٔ اولیه برای اجرا انتخاب شده است: تست رقابت هم‌زمان برای `mark_read` و بررسی نتیجهٔ نهایی در PostgreSQL.
- گسترش F-03 فراتر از این قرارداد نیازمند inventory جداگانهٔ شکاف‌ها و بازبینی مالک است.
